# 조리 완료 재전송: DB 변경 없이 가능한 대안

사용자는 운영 DB 스키마 변경을 현재 규모에 비해 큰 작업으로 판단했다. 이 PR은 대안 비교 문서이며 조리 완료 API·DB·Redis 동작을 변경하지 않는다. 기준 dev `d3ae87ab`다.

## 1. 응답이 없다고 처리도 없었던 것은 아니다

가상 예시:

1. 앱이 조리 완료 POST를 보낸다.
2. 서버가 조리 기록·평점·점수·냉장고 차감을 DB에 저장하고 commit한다.
3. 서버 응답이 네트워크에서 유실된다.
4. 앱은 실패로 보지만 서버에는 이미 성공한 결과가 있다.
5. 같은 요청을 다시 보내면 기존 코드가 또 수행될 수 있다.

예를 들어 기본 보상 5점이 두 번 지급될 수 있고 재료 100을 두 번 차감할 수 있다. 실제 점수·보너스는 미션/첫 조리 조건에 따라 다르다. 운영에서 이러한 중복 건수를 확인한 것은 아니다.

## 2. 기존 잠금은 어떤 역할인가

[RecipeCommandServiceImpl](../../src/main/java/com/mohaemukzip/mohaemukzip_be/domain/recipe/service/command/RecipeCommandServiceImpl.java)의 `createCookingRecord`는 회원 행과 레시피 행을 잠근다. 같은 회원의 두 요청은 한 번에 값을 덮어쓰는 경쟁을 피할 수 있지만, 잠금 뒤에 처리되는 두 번째 요청이 앞 요청의 재전송인지는 알 수 없다.

같은 날짜·회원·recipeId·rating으로 비교해도 두 번 실제 조리한 정상 요청일 수 있다. '5초 안에 같은 요리면 중복' 같은 조건은 정확한 식별이 아니라 정상 요청을 막을 수 있는 추정이다.

## 3. 현재 규모에서 대안 비교

| 방안 | DB 스키마 변경 | 줄일 수 있는 문제 | 보장하지 못하는 것 |
|---|---|---|---|
| 앱에서 완료 버튼 처리 중 비활성화 | 없음 | 빠른 두 번 클릭 | 앱 재시작·응답 유실·다른 기기 재요청 |
| 앱의 POST 자동 재시도를 점검하고 불명 결과에서 기록 확인 | 없음 | 무작정 재전송 | 기존 조회만으로 요청의 주인이 누구인지 정확 식별 |
| 서버 메모리의 짧은 중복 캐시 | 없음 | 단일 인스턴스의 짧은 중복 | 재시작·여러 서버·DB commit과 캐시의 원자성 |
| 기존 Redis에 회원+요청 키+처리 상태/응답 캐시 | 없음 | 키가 남아 있는 동안 중복 실행 억제·결과 재사용 | Redis 장애/유실·TTL 만료·DB commit과 캐시 사이 실패 |
| 조리 변경과 요청 식별을 같은 DB 트랜잭션에 저장 | 필요 | 영속 요청 식별·결과 일관성 | 보관 기간·마이그레이션·앱 계약 등 추가 설계 |

**DB를 바꾸지 않는 방법도 있다.** 다만 Redis를 사용한다고 DB 부작용까지 원자적으로 '한 번만' 처리되는 것은 아니다. Redis 기반 중복 억제가 충분한지는 불명 결과 처리 정책부터 선택해야 한다.

## 4. Redis 방식에서 놓치기 쉬운 두 구간

### DB commit 뒤에 결과를 캐시

`Redis 선점 → 기존 DB 조리 처리·commit → Redis 응답 저장 → 앱 응답`

DB commit 뒤 Redis 응답을 남기기 전에 서버가 종료되면, DB에는 결과가 있지만 Redis에는 완료 표시가 없다. 선점 TTL이 만료된 후 무조건 새 실행을 허용하면 다시 차감할 수 있다.

### DB commit 전에 결과를 캐시

`Redis 선점 → Redis 완료 표시 → DB commit 실패`

캐시만 보면 성공인데 DB 변경은 롤백될 수 있다. 결과 캐시를 앞으로 옮기는 것만으로 해결되지 않는다. 기존 트랜잭션 서비스의 정상 반환과 실제 commit 완료 시점도 구분해야 한다.

### 잠금 TTL과 작업 시간

잠금이 DB 처리보다 먼저 만료되면 새 작업이 들어올 수 있다. 예전 요청이 늦게 잠금을 지울 때 새 요청의 잠금을 지워서도 안 된다. 소유 토큰을 비교해 해제하고 전체 처리 시간/만료/연장 정책을 검토해야 한다.

Redis의 원자적 저장·스크립트는 **Redis 안의 연산**을 묶는다. MySQL commit까지 같은 원자 연산으로 묶는 것은 아니다. 새 분산 잠금 라이브러리를 도입하자는 제안은 아니다.

## 5. DB 변경 없는 작은 추천 순서

### 지금: 앱의 실제 재시도 경로 확인

- 요청이 진행 중일 때 완료 버튼을 중복 활성화하는지.
- 네트워크 라이브러리·앱 로직이 조리 POST를 자동 재전송하는지.
- 응답 없음과 확정 실패를 같은 안내로 표시하는지.
- 기존 조리 기록 조회로 사용자가 먼저 결과를 확인할 수 있는지.

이 저장소는 백엔드이므로 실제 앱의 재시도 코드는 이번에 읽거나 수정하지 않았다. '자동 재시도가 있다'고 단정하지 않는다.

### 다음: Redis 중복 억제를 선택할 경우 먼저 합의

- 한 번의 조리 의도로 만든 키를 재전송에도 유지. 새 조리는 새 키.
- 키 없는 기존 앱은 현행 동작을 유지하므로 중복 방지가 적용되지 않는다는 한계 표시.
- 같은 회원+키에 다른 recipe/rating은 충돌 처리.
- 진행 중은 즉시 다시 조리하지 않고 상태 안내.
- 결과가 불명확한 요청은 재실행하거나 성공으로 단정하지 않고 확인 대상으로 안내.
- Redis 장애 때 기존 조리를 허용할지, 키 있는 요청을 일시 거절할지 결정.
- TTL 이후 보장 범위와 캐시 보관 목적·개인정보를 정함.

이 정책을 선택하면 새 DB 컬럼 없이 시작할 수 있다. 그러나 캐시가 사라진 뒤에도 영속적으로 동일 조리 의도를 식별하는 기능은 아니다. 불명 결과에서 사용자 확인이 필요할 수 있어, 정책 확정 전 코드를 추가하지 않았다.

### 나중: 문제가 관찰되고 더 강한 보장이 필요할 때

기존 스키마 확장·이전 데이터·회원 탈퇴·키 보관 기간·같은 트랜잭션의 응답 스냅샷을 별도 과제로 검토한다. 지금 Kafka·분산 트랜잭션·새 인프라 도입을 요구하지 않는다.

## 6. 재시도와 새로운 조리를 구분하는 예시

| 요청 | 의도 | 기대 처리(선택 키 방식을 구현한다면) |
|---|---|---|
| 요청 A: 키 cook-1, 레시피 7, 별점 4 | 첫 조리 | 1회 처리 |
| 요청 B: 같은 키 cook-1, 같은 입력 | 응답 유실 재전송 | 결과가 확인되면 기존 응답, 추가 차감 없음 |
| 요청 C: 같은 키 cook-1, 별점 5 | 키를 다른 입력에 재사용 | 충돌 |
| 요청 D: 새 키 cook-2, 같은 레시피/별점 | 실제 두 번째 조리 | 새 조리 허용 |
| 요청 E: 키 없음 | 기존 앱 요청 | 현재 계약 유지, 중복 식별 보장 없음 |
| 요청 F: DB는 성공했지만 Redis 결과가 없음 | 불명확 | 자동 재실행·성공 단정 금지, 확인 정책 필요 |

위 기능은 구현된 API가 아니라 선택안이다. 이 문서는 테스트 통과나 운영 중복 방지 완료를 주장하지 않는다.

## 7. 공식 자료·기술 자료와 적용 한계

- [RFC 9110, 9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2): 비멱등 요청의 자동 재시도는 처리 의미를 알고 판단해야 한다. POST를 PUT으로 이름만 바꿔도 사업 로직이 멱등해지는 것은 아니다.
- [Redis 공식 잠금 패턴](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/): 잠금 만료·소유 토큰·안전한 해제를 검토하는 근거. Redis와 MySQL의 일괄 commit 보장을 제공하는 문서로 해석하지 않는다.
- [AWS Builders' Library 원문 PDF](https://d1.awsstatic.com/builderslibrary/pdfs/making-retries-safe-with-idempotent-apis-malcolm-featonby.pdf): 호출자 요청 ID·동일 의도·의미가 같은 응답과 요청 식별/부작용의 원자성을 참고한다. EC2 구현이나 다른 서비스의 보장 수준을 현재 코드에 그대로 적용하지 않는다.

## 8. 면접에서 설명할 수 있는 범위

“조리 완료의 회원 행 잠금은 동시 값 갱신을 제어하지만 응답 유실 뒤 재전송까지 같은 작업으로 식별하지는 못했습니다. 현재 규모에서 DB 변경을 피하기 위해 앱의 중복 클릭/자동 재시도 점검과 기존 Redis의 요청 키·응답 캐시를 비교했습니다. DB commit 뒤 캐시 저장 전 종료되는 구간 때문에 Redis만으로 정확히 한 번을 보장한다고 말할 수 없었고, 불명 결과의 처리 정책을 먼저 결정하도록 설계안을 정리했습니다.”
