# 레시피 분량·단위: 문제와 정책 선택안

이 문서는 동작 변경이 아닌 검토 자료다. 사용자는 수량 불명 정책을 아직 확정하지 않았으므로 분량 파싱·표시·자동 차감 코드를 바꾸지 않는다. DB 스키마와 운영 데이터도 변경하지 않는다. 기준은 dev `d3ae87ab`다.

## 1. 먼저 이해할 한 예시

아래는 가상 반례다. 운영 DB의 양파 단위가 g라고 확인한 것은 아니다.

- 영상 원문: **양파 1개**.
- 가정한 마스터: `Ingredient.unit=GRAM`, 회원 냉장고 보유량 400g.
- 현재 프롬프트: 단위를 빼고 `amount="1"`을 반환하도록 지시.
- 저장: `RecipeIngredient.amount=1.0`. 원본 단위 '개'는 보관되지 않는다.
- 상세 응답: 저장된 amount와 마스터 unit을 합쳐 **1g**처럼 표현될 수 있다.
- 조리 완료: 수량을 그대로 빼서 **400 - 1 = 399**.

핵심은 숫자 1이 틀렸다는 게 아니라, **1개를 1g으로 해석할 근거를 잃었다는 것**이다. 양파 1개의 무게를 임의로 200g이라고 정하는 것도 확인된 해결이 아니다.

## 2. 현재 코드의 연결

1. [RecipeCrawler](../../src/main/java/com/mohaemukzip/mohaemukzip_be/domain/recipe/service/crawler/RecipeCrawler.java)의 prompt는 '200g→200, 1개→1', '적당량→1', '분량 없음→1'을 지시한다. 입력 재료 목록도 이름 위주라 기준 단위를 모델에 충분히 전달하지 않는다.
2. [RecipeIngredientConverter](../../src/main/java/com/mohaemukzip/mohaemukzip_be/domain/recipe/converter/RecipeIngredientConverter.java)는 `Double.valueOf`로 수량을 읽는다. 값 없음/파싱 실패는 null이다. NaN/Infinity 같은 특별 값도 수용 가능한 변환 메서드다.
3. [RecipeDetailConverter](../../src/main/java/com/mohaemukzip/mohaemukzip_be/domain/recipe/converter/RecipeDetailConverter.java)는 amount와 `Ingredient.unit.getLabel()`을 응답한다.
4. [RecipeCommandServiceImpl](../../src/main/java/com/mohaemukzip/mohaemukzip_be/domain/recipe/service/command/RecipeCommandServiceImpl.java)의 `deductMemberIngredients`는 RecipeIngredient.amount를 MemberIngredient.weight에서 직접 뺀다.
5. [MemberIngredient](../../src/main/java/com/mohaemukzip/mohaemukzip_be/domain/ingredient/entity/MemberIngredient.java)는 보유 weight가 null일 때 양수를 차감하면 weight를 0으로 만들며, 서비스는 비었다고 판단해 삭제할 수 있다.

`weight`라는 필드 이름만으로 모든 저장 값이 g라고 단정할 수 없다. 마스터에는 g/ml/개/팩/공기 등 [여러 단위](../../src/main/java/com/mohaemukzip/mohaemukzip_be/domain/ingredient/entity/enums/Unit.java)가 있다. 실제 앱 입력 규칙과 데이터 샘플을 대조해야 한다.

## 3. 서로 다른 문제를 나누기

| 상황 | 예시 | 필요한 판단 |
|---|---|---|
| 같은 단위 | 원본 200g, 기준 g | 근거가 맞다면 200을 그대로 사용 가능 |
| 같은 종류의 단위 환산 | 원본 0.2kg, 기준 g | 0.2×1000=200g. 원본 단위를 보존해야 함 |
| 다른 종류의 단위 | 원본 1개, 기준 g | 재료별 개수/무게 근거 없이는 환산 불가 |
| 부피/무게 | 물 200ml, 기준 g | 재료별 밀도·조건 근거 필요. 모든 재료에 1:1 적용 금지 |
| 추정 수량 | 소금 적당량 | 숫자 1이 관찰한 양이 아니라 임의 추정임을 구분 |
| 사용량 불명 | 영상에 분량 없음 | 레시피 amount 불명과 실제 0을 구분 |
| 보유량 불명 | 냉장고에는 있다고만 등록 | MemberIngredient.weight 불명은 재료 미보유와 다름 |
| 비정상 숫자 | NaN, Infinity, 음수 | 단위 문제와 별개로 유효 숫자 경계 확인 |

'수량을 모르면 차감하지 않기'는 위의 사용량 불명에 대한 제안이었다. **보유량 불명·원본 단위 소실·표시 의미까지 자동으로 해결되는 정책은 아니다.**

## 4. 왜 바로 전체 정책을 바꾸지 않는가

400g의 냉장고가 있는 경우에 사용량이 불명이라 차감을 건너뛰면 보유량이 과대 표시될 수 있다. 반대로 근거 없이 1g을 차감하면 차감한 척하는 잘못된 정밀도를 제공한다. 불명 레시피를 모두 등록 거절하면 이용할 수 있는 레시피 수가 줄 수 있다. 필요한 UX와 데이터 신뢰도를 먼저 선택해야 한다.

| 선택안 | 장점 | 남는 문제·영향 |
|---|---|---|
| 확실한 수량만 차감, 불명은 표시 후 건너뜀 | 근거 없는 환산 방지. 기존 amount nullable 활용 가능 | 재고가 실제보다 많아질 수 있음. 앱의 null/불명 표시 확인 필요 |
| 사용자에게 조리 후 사용량 확인 | 실제 사용량을 반영할 수 있음 | 앱 화면·추가 입력 필요, 바로 도입하기에는 범위 큼 |
| 불명 수량은 관리자 검수 후 등록 | 품질 높은 등록 자료 구축 | 관리자 작업 증가, 기존 데이터 처리 정책 필요 |
| 불명 포함 레시피 등록 전체 거절 | 시스템 데이터가 명확해짐 | 분량이 없는 영상도 모두 거절될 수 있음 |
| 재료별 표준 개수/무게 추정 | 편의성 | 추정값을 실제 측정처럼 쓰면 안 됨. 근거·버전·오차 관리 필요 |

사용자는 아직 선택하지 않았다. 본 문서는 추천을 확정 정책으로 표현하지 않는다.

## 5. 지금 규모에서 가능한 작은 순서

1. 운영 변경 없이, 기존 레시피 3~5개의 원문/마스터 단위/amount/회원 입력 기준을 사람이 비교한다. 이번에는 운영 데이터를 조회하지 않았다.
2. 단위 정책과 별개로 유한수·양수 검사 범위를 별도 작은 이슈로 검토한다. 파싱 실패와 실제 수량 불명을 구분할 수 있는 로그/검수 기준도 정한다.
3. 정책 합의 후 내부 AI 결과에 원본 단위와 수량을 전달하고, 서버에서 같은 단위/확실한 같은 차원 환산만 처리하는 안을 검토한다. 내부 DTO 변경과 nullable amount를 이용하면 첫 단계에서 새 DB 컬럼 없이 시작할 수 있다.
4. 원본 값 영속화와 기존 수량 재계산은 다음 단계다. 기존 데이터는 근거를 복원하기 전 자동 보정하지 않는다.

프롬프트에 단위 필드를 더해도 모델이 원문과 다르게 답할 수 있다. 타입 검증과 자막/설명 근거 검수는 따로 필요하다.

## 6. 학습용 비교표

| 비교할 값 | 예시 A | 예시 B | 예시 C |
|---|---|---|---|
| 영상 원문 | 양파 1개 | 양파 0.2kg | 소금 적당량 |
| 가정한 기준 단위 | g | g | g |
| 현재 숫자만 남기기 | 1 | 0.2 | 1(추정) |
| 안전한 계산 근거 | 없음 | kg→g=1000배 | 없음 |
| 다음 선택 | 원본 단위 확인·환산/불명 정책 | 200g으로 정규화 검토 | 추정값 표시/차감 정책 합의 |

오늘 종료 기준은 '어떤 입력에서 왜 숫자만 남기면 문제가 되는가'를 설명하는 것이다. 전체 자동 차감 정책을 당장 고르는 것은 아니다.

## 7. 근거와 적용 한계

- [Gemini Structured Output](https://ai.google.dev/gemini-api/docs/structured-output): 출력 형식 지원은 보조 수단이며 도메인 값·원문 근거 검증은 서버가 따로 설계해야 한다.
- [2026 레시피 데이터 구조 프리프린트](https://arxiv.org/abs/2609.22099): 재료 이름·수량·단위·상태를 나누는 표현 관점을 참고한다. 영양 DB 매핑·문화별 단위와 보고된 성능을 현재 서비스로 이전하지 않는다.
- [2025 EMNLP 절차 텍스트 논문](https://aclanthology.org/2025.findings-emnlp.1052/): 재료·과정의 일관성과 실행 가능성을 수동 검수 기준에 참고한다. 레시피 변경 과제이므로 영상 요약·재고 정확도를 직접 보장하는 자료는 아니다.

## 8. 면접에서 설명할 수 있는 범위

“분량을 숫자로만 저장하면 원본 단위가 사라지고 기준 단위와 결합되어 다른 양처럼 해석될 수 있는 경로를 확인했습니다. 사용량 불명과 보유량 불명도 다른 문제였습니다. 아직 운영 데이터와 정책이 확정되지 않아 자동 차감 코드를 바꾸지 않았고, 구체적 반례와 DB 변경 없이 시작할 수 있는 단계별 선택안을 작성했습니다.”

운영 피해·오류율·개선 수치를 측정한 것처럼 표현하지 않는다.
